## 🤔 **문제 정의**

1. **대용량 파일을 서버 내부 저장소에서 직접 관리해도 괜찮을까?**
   - 파일을 서버에 직접 저장하면 디스크 사용량 증가와 파일 관리 부담이 발생할 수 있음
   - 서버는 비즈니스 로직과 메타데이터 관리에 집중하고, 실제 파일 저장은 외부 스토리지로 분리할 필요가 있다고 판단함
1. **서버와 S3 간 파일 입출력 흐름을 안정적으로 구성할 수 있을까?**
   - 업로드와 다운로드 요청마다 S3와 통신해야 하므로 파일 저장 로직이 서비스 로직과 강하게 결합될 가능성이 있음
   - 파일 저장소 연동 로직을 별도 모듈로 분리하여 유지보수성과 확장성을 확보할 필요가 있음
1. **대용량 파일 다운로드를 서버에서 안정적으로 처리할 수 있을까?**
   - 대용량 파일을 처리할 때 메모리 사용량과 응답 시간이 문제가 될 수 있음
   - 단일 파일과 다중 파일 다운로드 상황을 구분하여 안정적인 응답 구조를 설계할 필요가 있음
1. **브라우저 환경에서 파일 다운로드 응답을 정확하게 처리할 수 있을까?**
   - 단순 byte 응답만으로는 파일명, 파일 크기, 다운로드 동작을 명확히 제어하기 어려움
   - HTTP 응답 헤더를 구성하여 사용자가 정상적으로 파일을 내려받을 수 있도록 처리할 필요가 있음

## 🥸 **설계 선택**

1. **파일 저장소를 서버와 분리하기 위해 AWS S3를 적용함**
   - 실제 파일은 S3에 저장하고, 서버 DB에는 파일 메타데이터와 S3 object key만 저장하도록 구성함
   - 서버 저장소와 파일 저장소의 역할을 분리하여 서버 부하와 파일 관리 부담을 줄이고자 함
1. **서버–S3 간 파일 통신 모듈을 서비스 계층으로 분리함**
   - S3 업로드, 다운로드 요청 생성 로직을 별도 서비스로 구성함
   - 비즈니스 로직에서는 object key를 기준으로 파일을 요청하도록 하여 저장소 접근 책임을 분리함
1. **단일 파일과 다중 파일 다운로드 흐름을 분기함**
   - 파일이 1개인 경우 원본 파일 형태로 반환함
   - 파일이 여러 개인 경우 서버에서 ZIP 파일로 묶어 하나의 다운로드 응답으로 반환하도록 구성함
1. **ResponseEntity와 HttpHeaders 기반 다운로드 응답 구조를 적용함**
   - `Content-Disposition`, `Content-Length`, `Content-Type` 헤더를 구성하여 브라우저가 파일 다운로드로 인식하도록 처리함
   - 파일명이 깨지지 않도록 인코딩 처리하여 사용자 다운로드 경험을 개선함

- `Content-Disposition` 기반 다운로드 응답 헤더를 구성하여 브라우저 환경에서 정상적인 파일 다운로드가 가능하도록 구현함
### 성과
- 🥈 2024 소중한 오픈소스 활용 SW경진대회 은상
### 🧐 무엇을 배웠나
1. **파일 저장소와 서비스 서버의 역할 분리가 중요함을 확인함**
   - 파일을 서버 내부에서 직접 관리하지 않고 S3로 분리하면서 서버는 메타데이터와 인증 처리에 집중할 수 있었음
   - 저장소 연동 책임을 분리하면 향후 저장 방식이 변경되어도 서비스 로직의 영향 범위를 줄일 수 있음을 확인함
2. **파일 다운로드는 단순 조회가 아니라 응답 구조 설계가 필요함을 확인함**
   - 다운로드 응답에서는 파일 내용뿐 아니라 파일명, 크기, `Content-Type`, `Content-Disposition` 같은 헤더 구성이 중요함
   - HTTP 응답 헤더 구성에 따라 브라우저에서의 다운로드 경험이 달라진다는 점을 확인함
3. **다중 파일 다운로드는 별도 처리 흐름이 필요함을 확인함**
   - 여러 파일을 각각 내려받도록 하는 방식보다 ZIP으로 묶어 반환하는 방식이 사용자 경험 측면에서 더 적합하다고 판단함
   - 단일 파일과 다중 파일 다운로드를 같은 API 내부에서 분기 처리하여 클라이언트의 요청 구조를 단순화할 수 있었음
4. **대용량 파일 처리에서는 메모리 사용과 응답 시간을 함께 고려해야 함을 확인함**
   - 파일 데이터를 서버에서 처리할 때 전체 데이터를 메모리에 적재하는 구조는 파일 크기가 커질수록 부담이 커질 수 있음
   - 이후에는 스트리밍 다운로드, Presigned URL, multipart upload 같은 구조로 확장할 필요성을 확인함
5. **낯선 백엔드 기술도 공식 문서 기반으로 구조를 이해하며 적용할 수 있음을 확인함**
   - Spring Boot와 AWS S3를 처음 사용하는 프로젝트였기 때문에 초기에는 파일 업로드, S3 object key 관리, 다운로드 응답 구성 방식에 대한 이해가 부족했음
   - AWS SDK와 Spring Boot 공식 문서를 기준으로 파일 처리 흐름을 정리하고, AI 도구를 보조적으로 활용하여 구현 방향을 검토함
   - 이 과정에서 단순히 예제 코드를 복사하는 것이 아니라 업로드 요청 생성, object key 저장, 다운로드 응답 헤더 구성까지 전체 파일 처리 흐름을 구조적으로 이해하며 구현할 수 있었음

## 🛠️ 핵심 시스템 {#impl}

### 📦 파일 메타데이터 DB 구조
  
파일 데이터는 AWS S3에 저장하고 DB에는 파일 접근에 필요한 메타데이터만 저장하도록 구성함

| 필드명           | 설명               |
| ------------- | ---------------- |
| id            | 파일 식별자           |
| file_name     | 사용자 다운로드 파일명     |
| size          | 파일 크기            |
| password      | 다운로드 접근 제어용 비밀번호 |
| s3_object_key | S3 저장 경로         |
| created_at    | 업로드 시각           |

### 1. AWS S3 기반 파일 저장 구조 구현

```java
public void uploadFile(MultipartFile file, String keyName) {
    ObjectMetadata metadata = new ObjectMetadata();
    metadata.setContentLength(file.getSize());
    metadata.setContentType(file.getContentType());

    amazonS3Client.putObject(
        bucketName,
        keyName,
        file.getInputStream(),
        metadata
    );
}
```

- 파일 업로드 요청 시 서버 로컬 저장소가 아닌 AWS S3 버킷에 직접 저장하도록 구성함
- 업로드 과정에서 `ObjectMetadata`를 설정하여 파일 크기와 MIME 타입을 함께 관리하도록 구현함
- 파일 저장 위치는 DB에 object key 형태로 저장하고 실제 파일 데이터는 S3에서 관리하도록 저장 구조를 분리함

---

### 2. 서버–S3 간 파일 통신 모듈 구현

```java
public S3Object downloadFile(String keyName) {
    return amazonS3Client.getObject(bucketName, keyName);
}
```

- 다운로드 요청 시 object key 기반으로 S3에서 파일을 조회하도록 구현함
- 서비스 계층에서는 파일 저장 위치를 직접 다루지 않고 key 기반으로 요청하도록 구성함
- 저장소 접근 로직을 별도 모듈로 분리하여 서비스 계층과 스토리지 계층의 책임을 분리함

---

### 3. 대용량 파일 다운로드 처리 구조 구현

```java
@PostMapping("/downloads/{id}")
public ResponseEntity<?> downloads(
    @PathVariable("id") Long id,
    @RequestBody Password body
) {
    S3FileDetails fileDetails =
        s3Service.downloadFile(id, body.password());

    HttpHeaders responseHeader =
        DownloadResponseBuilder.getResponseHeader(
            fileDetails.fileName(),
            fileDetails.size()
        );

    return new ResponseEntity<>(
        fileDetails.content(),
        responseHeader,
        HttpStatus.OK
    );
}
```

- 다운로드 요청 시 파일 ID와 비밀번호를 기반으로 접근 검증 이후 파일 데이터를 반환하도록 구성함
- 파일 메타데이터 조회 → S3 다운로드 요청 → HTTP 응답 생성 흐름으로 다운로드 구조를 분리함
- 파일 다운로드 과정에서 서비스 계층과 저장소 계층의 책임을 분리하여 처리함

---

### 4. HTTP 다운로드 응답 헤더 구성 구조 구현

```java
public static HttpHeaders getResponseHeader(
    String fileName,
    long size
) {
    HttpHeaders headers = new HttpHeaders();

    headers.setContentDisposition(
        ContentDisposition.builder("attachment")
            .filename(fileName)
            .build()
    );

    headers.setContentLength(size);
    headers.setContentType(
        MediaType.APPLICATION_OCTET_STREAM
    );

    return headers;
}
```

- `Content-Disposition` 헤더를 설정하여 브라우저에서 파일 다운로드 응답으로 인식하도록 구성함
- 파일 크기(`Content-Length`)와 MIME 타입(`Content-Type`)을 함께 설정하여 다운로드 안정성을 확보함
- 응답 헤더 생성 로직을 별도 유틸 클래스로 분리하여 다운로드 응답 구조를 재사용 가능하도록 구현함
